3. (버그수정) 말풍선 영역별 OCR 결과의 좌표를 pymupdf dict 구조로 변환하는 과정에서

4. (개선) pymupdf 내장 OCR API는 PSM(페이지 분할 모드)을 노출하지 않는데, 실제
   테스트로 PSM 선택이 인식 정확도에 큰 영향을 준다는 걸 확인했다. tesseract
   CLI를 직접 호출해 여러 PSM(6,3,11)을 시도하고 스크립트 신뢰도가 가장 높은
   결과를 채택하도록 개선(tesseract 미설치 시 기존 pymupdf 내장 OCR로 자동 폴백).
5. (버그수정) 말풍선 하나가 OCR 결과 특성상 표/다단으로 오판되어 여러 줄로 쪼개진
   뒤, 그중 애매한 조각 하나(예: 인식 오류로 생긴 이상한 기호)가 신뢰도 검사에
   실패하면 나머지 멀쩡한 줄들까지 통째로 폐기되는 문제 수정. OCR 결과는 원본
   PDF 텍스트보다 좌표가 부정확하므로 표 판정 허용치를 대폭 완화, 정상 문단이
   먼저 하나로 합쳐지도록 했다.
6. (개선) OCR 신뢰도 검사를 페이지 전체 단위에서 "말풍선(블록) 단위"로 세분화 -
   말풍선 일부(가로쓰기)는 정확히 인식되고 다른 일부(세로쓰기)만 실패하는 흔한
   경우, 이전엔 페이지 전체가 폐기됐지만 이제 실패한 말풍선만 개별 폐기하고 성공한
   말풍선은 그대로 살린다. 단, 후보 수가 적은 블록은 우연히 임계값을 넘기 쉬워
   기준을 더 엄격하게 적용해 만화의 노이즈가 새어나오는 걸 최대한 억제한다.
   (※ 한계: "형식은 맞지만 의미 없는 글자 조합"은 문자 단위 규칙으로 완벽히 걸러낼
   수 없다는 게 이번 세션에서 재확인됐다 - 실제 언어모델 수준 검증 없이는 근본
   해결이 어려운 한계로 남아있다.)

V5.6
1. (신기능) 일본어 만화 전용 OCR "manga-ocr"(kha-white/manga-ocr) 선택적 통합.
   manga-ocr은 Tesseract보다 일본어 만화 텍스트(세로쓰기, 후리가나, 이미지 위
   텍스트, 장식체 폰트)에 훨씬 강하지만, 모델 자체가 일본어 전용으로만 학습돼
   있어 다른 언어(한국어/영어 등)는 전혀 지원하지 않는다 - 그래서 대체가 아니라
   하이브리드로 붙였다: --ocr-lang에 일본어(jpn/jpn_vert)가 포함되고 manga-ocr이
   설치돼 있으면 그 영역의 텍스트 인식만 manga-ocr로 대체하고, 다른 언어 영역과
   세로/가로 방향 판정(Tesseract의 줄 위치 구조 재사용), 안전 필터, 렌더링은 전부
   기존 파이프라인을 그대로 쓴다. manga-ocr 자체는 PyTorch 의존이라 무겁고(실측
   torch만 526MB) 최초 실행 시 모델(~400MB)을 인터넷에서 받아야 해서, 기본 EXE에는
   포함하지 않고 GUI의 "manga-ocr 설치(선택)" 버튼으로 별도 설치하도록 분리했다
   (build_exe.bat/requirements.txt에는 미포함 - 기본 EXE는 그대로 가벼움).
   설치 안 해도 기존처럼 100% 정상 동작한다(자동으로 Tesseract만 사용, 완전히
   투명한 폴백 - 실제 미설치/로드실패 상태 둘 다 검증함).

V5.5
1. (버그수정, 심각) 다국어 조합으로 OCR 언어를 지정하면(예: "jpn+jpn_vert+eng+kor" -
   실제 다국어 문서에서 정상적인 사용법) 정상적인 영어/한국어 텍스트가 통째로
   걸러지던 두 가지 버그를 수정했다.
     (a) _sanitize_ocr_text가 "jpn"이 언어 문자열에 포함되기만 하면 무조건 모든
         라틴 알파벳(2자 이상)을 제거해버렸다 - "WATCH OUT! THE ENEMY..."처럼
         완벽히 인식된 영어 문장이 전부 빈 문자열로 사라지는 원인이었음. eng이
         명시적으로 함께 지정된 경우엔 이 필터를 건너뛰도록 수정.
     (b) _ocr_script_plausibility가 elif 체인이라 "jpn"이 있으면 무조건 일본어
         문자만 검사하고 영어/한국어는 아예 확인을 안 했다(예: 순수 영어 텍스트가
         "일본어 문자 0개"라며 실패 판정됨). 지정된 언어 중 하나라도 매치하면
         인정하도록 합집합 판정으로 변경.
   실제 순수 이미지(텍스트 레이어 없음) 다국어 샘플로 확인: 위 수정 전엔 가로쓰기
   텍스트까지 전부 폐기됐는데, 수정 후 일본어/영어 가로쓰기 문장이 완벽에 가깝게
   복원됨("気をつけて!敵はすぐ後ろにいるぞ!", "WATCH OUT! THE ENEMY IS RIGHT
   BEHIND YOU!" 등).
2. (개선) pymupdf 내장 OCR API는 Tesseract의 PSM(페이지 분할 모드)을 노출하지
   않는데, 실제 테스트로 PSM 선택이 인식 정확도에 큰 영향을 준다는 걸 확인했다
   (특히 세로쓰기처럼 전용 모델이 부족한 경우). tesseract 실행파일이 있으면 CLI를
   직접 호출해 여러 PSM(6/3/11)을 시도하고 스크립트 신뢰도가 가장 높은 결과를
   채택하도록 변경(TSV 출력으로 줄 단위 위치정보까지 복원). tesseract가 없으면
   기존 pymupdf 내장 OCR로 자동 폴백.
3. (개선) OCR 신뢰도 검사를 "페이지 전체 통과율"이 아니라 "말풍선(블록) 단위"로
   세분화했다. 기존엔 한 페이지 안에 정상 인식된 말풍선과 실패한 말풍선이 섞여
   있으면 전부 다 폐기됐는데(예: 가로쓰기 3개는 완벽했는데 세로쓰기 3개가 실패하자
   전부 버려짐), 이제 말풍선별로 개별 판단해 정상 인식된 것은 살리고 실패한 것만
   개별 폐기한다. 만화처럼 페이지 전체가 노이즈인 경우는 모든 블록이 낮은 통과율을
   보여 결과적으로 동일하게 다 걸러지므로 기존 안전성은 그대로 유지된다.
4. (한계 확인, 참고) 세로쓰기 한국어/영어(전각)는 Tesseract에 전용 학습 모델이
   없어(kor_vert 자체가 존재하지 않음, jpn_vert만 있음) 위 개선들을 적용해도
   여전히 정확도가 낮다. 90도 회전 후 인식하는 방법도 시도해봤으나 한글 자모
   구조가 회전시 완전히 달라져 오히려 역효과였다(실측 확인). 세로쓰기 한국어/
   영어 정확한 번역이 필요하면 만화 전용 OCR 도구나 수동 전사 후 --import-json
   워크플로를 권장한다.

V5.4
1. (버그수정, 심각) 세로쓰기 번역문이 개발 환경에서는 잘 보이는데 실제 사용자
   PDF 뷰어에서는 글자가 거의 안 보이고 문장부호만 남는 문제 수정. 원인:
   page.insert_text(fontname="korea", ...)처럼 pymupdf 내장 별칭을 그대로 쓰면
   실제 폰트 파일이 PDF에 임베드되지 않고 "Dotum"이라는 시스템 폰트를 참조만
   하는 상태가 된다(실제 확인: get_fonts()에서 ext='n/a', embedded=0). 그 시스템
   폰트가 없는 뷰어에서는 글자가 안 보인다. pymupdf.Font()로 실제 폰트 바이너리를
   얻어 page.insert_font()로 명시적으로 임베드하도록 수정(ext='ttf'로 실제
   임베드되는 것 확인). 가로쓰기(insert_htmlbox 경로)는 원래부터 정상 임베드였다.
2. (버그수정, 심각) 번역문 위에 원문 글자 하나가 겹쳐 보이는 문제 수정. 원인이
   두 가지 겹쳐 있었다:
     (a) insert_htmlbox가 텍스트를 다 못 넣어(spare<0) "실패"로 처리되면 그
         아래 폴백(insert_textbox)으로 넘어가는데, mupdf Story가 들어간 부분은
         이미 실제로 그려놓은 상태라 폴백 결과가 그 위에 겹쳐져 이중으로 보임.
         모든 재시도/폴백 전에 해당 영역을 다시 지우도록 안전장치 추가.
     (b) 일부 PDF 생성 도구는 특정 글자를 텍스트로 넣으면서 동시에 그 글자와
         똑같은 위치에 SMask 처리된 작은 이미지(그 글자 모양의 래스터)도 겹쳐
         렌더링해둔다(실제 확인: 검은 2x2 픽셀 인덱스 이미지 + SMask). 텍스트만
         redact하고 이미지는 보존하는 정책(배경 사진 보호용) 때문에 이 중복
         이미지가 안 지워지고 남아 번역문과 겹쳐 보였다. 세그먼트 영역과 크게
         겹치면서 그보다 훨씬 작은 이미지만 골라 page.delete_image()로 제거하는
         안전장치를 추가했다(원본 삽화/사진처럼 세그먼트보다 큰 이미지는 그대로
         보존됨 - 이 조건에 안 걸림).
   실제 배경 없는 순수 텍스트 샘플로 재현 후 두 원인 모두 확인, 수정 후 재검증.

V5.3
1. (버그수정, 핵심) 세로쓰기(일본어 종서 등) 문서에서 pymupdf가 한 문장(말풍선)의
   서로 다른 컬럼을 완전히 별개의 물리 블록으로 나눠 제공하는 경우, 지금까지는
   전혀 병합되지 않고 낱글자 단위로 쪼개져 번역 품질이 크게 떨어졌다(배경 없는
   순수 텍스트 샘플로 실제 확인: 한 말풍선이 최대 8개 블록으로 쪼개짐). 기존
   "물리 블록은 절대 병합 안 함" 정책(V3.8)은 표/목차 문서를 지키기 위한
   것이었는데, 세로쓰기 문서에는 오히려 해가 됐다. 이번에 merge_adjacent_segments를
   "세로쓰기 세그먼트 전용" 안전 병합으로 되살렸다:
     - vertical=True인 세그먼트끼리만 병합 대상 (가로쓰기 표/문단은 전혀 영향 없음 -
       기존 안전성 그대로 유지, 회귀 없음 확인)
     - 두 가지 패턴 모두 처리: 여러 컬럼이 나란한 경우 + 한 컬럼이 위아래로 쪼개진 경우
     - 폰트 크기가 다르면(제목 vs 본문 등) 병합하지 않음
     - 이미 문장 종결부호(。！？. 등)로 끝난 "완결된 문장"은 옆 컬럼과 이어붙이지
       않음 - 이 조건이 없으면 서로 다른 독립 문장 9개가 나란히 배치된 문서에서
       전부 하나로 잘못 합쳐지는 심각한 회귀가 있었음(실제 발견 후 수정)
     - 병합 결과가 페이지의 다른 세그먼트를 침범하면 그 병합은 포기(안전 우선)
   실제 샘플(일본어/영어 전각/한국어 세로쓰기 혼합 문서)로 검증: 3개 말풍선 전부
   완전한 한 문장으로 정확히 병합, 기존 표/세로쓰기(9개 독립문장) 회귀 없음 확인.

V5.2
1. (신기능) 만화/일러스트 OCR을 "말풍선 영역 검출 후 개별 인식" 방식으로 개선.
   기존엔 페이지 전체를 통째로 OCR해서 그림(효과선/스크린톤)까지 글자로 오인하는
   노이즈가 컸다. 이제 opencv로 먼저 "밝은 배경의 독립된 영역"(말풍선처럼 보이는
   곳)을 이미지 분석으로 찾고, 그 영역만 별도로 잘라 개별 인식한다. 주변 그림의
   간섭이 줄어드는 효과가 있으나, Tesseract 자체의 만화체/세로쓰기 인식률 한계는
   여전히 남아있어 완벽하지 않을 수 있다 - 다만 기존 안전장치(스크립트 신뢰도,
   폰트 크기 이상치, 페이지 단위 신뢰도 검사)가 여전히 잘못 인식된 결과를 걸러내
   원본을 보호한다. requirements.txt에 numpy/opencv-python-headless 추가.
2. (버그수정, 심각) 이미 텍스트 레이어가 있는 PDF(외부 OCR 도구로 미리 인식시킨
   파일 등)는 그 내용이 쓰레기여도 우리 자체 OCR 안전장치가 전혀 발동하지 않던
   문제 수정. 원인: "텍스트가 20자 미만이면 스캔본으로 추정"하는 조건이, 이미
   (질 나쁜) 텍스트 레이어가 있는 페이지는 통과시켜버려서 안전장치 자체가 우회됐다.
   이제 이미지가 페이지 대부분을 차지하는데 기존 텍스트의 신뢰도가 낮으면(스크립트
   불일치 또는, 언어를 몰라도 텍스트 파편화 정도로 판단) 그 텍스트를 무시하고 자체
   재인식으로 대체한다.
3. (버그수정) 번역 대상이 0개(OCR 안전장치가 전부 폐기한 경우 등)면 예전엔 오류로
   프로그램이 죽었는데, 이제 정상 완료로 처리한다(원본 그대로 저장, 종료코드 0).
4. build_exe.bat에 numpy/cv2(opencv) 번들링 추가.

V5.1
1. (버그수정) OCR 안전장치가 정상 작동해 신뢰도 낮은 결과를 전부 폐기하면
   "번역할 텍스트가 없습니다"라는 치명적 오류로 프로그램이 죽어버리던 문제
   수정. 이제 번역 대상이 0개면 오류가 아니라 정상 완료로 처리한다 - 번역
   단계를 건너뛰고 원본 내용(그림 포함) 그대로 저장한 뒤 종료코드 0으로
   끝난다. 실제 만화 샘플로 확인: 그림/원문 전부 손상 없이 그대로 보존됨.
2. (버그수정, 심각) 원문 언어를 "자동 인식"으로 두면 OCR 오탐이 훨씬 심하게
   새어나가던 문제 수정. 원인: 언어를 모르면 OCR 언어가 무작정 영어(eng)로
   매핑됐는데, 영어 판정 필터("이 글자가 라틴 알파벳인가")는 CJK 범위 검사와
   달리 판별력이 거의 없어서(Tesseract가 만화 그림에서 뽑아낸 아무 글자
   나열이든 전부 라틴 알파벳이라 필터를 그대로 통과함) 훨씬 많은 쓰레기
   텍스트가 번역까지 진행돼버렸다(실제로 영문 잡음이 한국어로 잘못 "번역"
   되어 뒤섞이는 것까지 확인됨). 이제 원문 언어가 자동 인식/불명 상태면
   OCR 자체를 시도하지 않고, 실제 언어를 지정하라는 안내만 출력한다.
   --source-lang(예: Japanese)이나 --ocr-lang을 명시하면 그대로 정상 동작.

V5.0
1. 코드 전면 모듈화: translate_pdf.py(2727줄 단일 파일)를 기능별 pdf_engine/
   패키지로 분리했다. translate_pdf.py는 이제 얇은 파사드(CLI 진입점 + 하위
   호환 재노출)만 남고, 실제 구현은 다음 모듈에 나뉘어 있다:
     pdf_engine/config.py          - 버전, 경로, 실행중단(STOP) 제어, 런타임 레지스트리
     pdf_engine/segment.py         - Segment 데이터클래스
     pdf_engine/extraction.py      - PDF/OCR 텍스트 추출, 표/세로쓰기 판정
     pdf_engine/batching.py        - 배치 구성, 프롬프트 생성
     pdf_engine/providers_cloud.py - Anthropic/Gemini/OpenAI 클라이언트, 키 풀, LLM 호출
     pdf_engine/providers_local.py - Lemonade/Ollama/LM Studio 로컬 런타임 관리
     pdf_engine/scheduler.py       - 배치를 provider에 분배해 번역 실행
     pdf_engine/rendering.py       - 번역문 PDF 재삽입, 세로쓰기/OCR 렌더링
     pdf_engine/io_utils.py        - 용어집, 페이지 범위, 번역 결과 내보내기/가져오기
     pdf_engine/filenaming.py      - 이어서-번역 파일명 규칙, 진행정보 사이드카
   `from translate_pdf import extract_segments` 같은 기존 참조는 그대로 동작한다
   (파사드가 전부 재노출). CLI 실행(`python translate_pdf.py ...`)도 동일.
   build_exe.bat에 pdf_engine 폴더를 --add-data/--hidden-import로 추가했다.
2. (버그수정, 심각) 만화/일러스트 OCR이 그림을 검은 상자로 뒤덮던 문제 수정.
   원인 두 가지: (a) 배경색 추정이 갑옷 등 어두운 그림을 "배경색=검정"으로
   오인해 큰 검은 사각형을 그렸음, (b) 일반 OCR(Tesseract)이 후리가나/효과음
   장식체/효과선까지 글자로 오인해 쓰레기 텍스트를 뽑았음. 문자 스크립트
   검사만으로는 "형식은 CJK이지만 의미 없는 조합"까지 못 걸러서, 폰트 크기
   이상치 필터(정상 말풍선은 8~16pt인데 오탐은 대부분 20pt+ - 페이지의 폰트
   크기 중앙값 대비 상대적으로 판정해 일반 스캔 문서의 큰 제목까지 걸러지는
   회귀는 방지)와 페이지 단위 신뢰도 검사(OCR 후보 대비 통과율이 너무 낮으면
   그 페이지의 OCR 결과를 통째로 폐기, 그림은 절대 건드리지 않음)를 추가했다.
   실제 만화 샘플로 검증: 15개 OCR 후보 중 13개(87%)가 쓰레기로 걸러져
   최종 신뢰도 12%로 판정 -> 페이지 전체 OCR 결과 자동 폐기, 원본 보존.
