# AutoCheck V0.5.9 최적화 계획

## 요약

**0~3단계 완료.** 앱의 최대 CPU 소비처였던 로그 판정 엔진(`engine/log_rule_engine.py`)이 **2.72배 빨라졌다**(`analyze_text` 70.2 → 25.8 ms). 시작 경로에서 미사용 의존성 3개(pandas/paramiko/openpyxl)를 걷어냈고, 유휴 폴링 빈도를 1/5로 줄였다. 테스트 0개에서 **272개**가 됐다(3단계까지 포함).

이 계획의 가장 중요한 발견은 **가장 그럴듯한 최적화가 실제로는 퇴행**이었다는 것이다. "정규식 31개를 단일 alternation으로 합친다"는 실측 2.6배 느림(Python `re`가 패턴별 리터럴 접두사 최적화를 잃고 모든 위치에서 백트래킹한다). 성립한 해법은 **줄 단위 메모화**였고, 그것도 **회차 전체가 메모를 공유해야** 의미가 있다 — 파일 단위 메모는 1.05배로 사실상 무의미하다.

3단계는 **측정으로 절반이 걸러졌다**. 3-3(워크스페이스 단일 스캔)은 약 2배 개선으로 적용했고, **3-4와 3-5는 실측 이득이 1 ms 대라 폐기**했다(3-5는 점검 직후 30초 낡은 수치라는 기능 후퇴까지 따라온다). 나머지는 모두 적용했다:

- ~~**3-2 반복 파싱 캐시**~~ — **완료.** 흐름 전체 약 2배(장비 30대 181.6 → 88.0 ms).
- **3-1 실시간 폴링 payload** ✅ — 장비 30대에서 877 → 12.2 KB/s(**72배**). 계산은 1.5 ms로 이미 싸서, 줄인 것은 전송량과 DOM 전면 재구축이다. 세 패널의 스냅샷 원자성은 델타 절단선과 섹션 지문을 같은 락 블록에서 파생시켜 유지했다.
- ~~**3-6 타임스탬프 포맷 통일**~~ — **완료(범위 수정).** 계획의 전제(포맷 혼재)는 재현되지 않았고, 실제 위험이던 파일명 파서 4중 복제를 통합하고 정렬 불변식을 테스트로 고정했다.

### 0-2. 재현 가능한 벤치마크 하네스 ✅

- **파일**: `tools/synthetic_log.py`(코퍼스 생성), `tools/bench_log_analysis.py`(측정/비교), `tests/test_bench_harness.py`(38 tests). 기준선(`tools/bench_baseline.json`)은 gitignore — 머신마다 절대값이 3배 이상 다르므로 각자 `--save-baseline` 으로 만든다.
- **기능**: 고정 시드 합성 로그(장비 수·중복률 파라미터) + `analyze_text` 및 단계별 타이밍 + 메모 이득(파일 단위 / 회차 공유 분리) + `RealtimeMonitor.state()` payload를 장비 4/12/30대로 측정. `--save-baseline` / `--check`(임계값 10% 초과 퇴행 시 exit 1) / `--json`.
- **대표값은 평균이 아니라 최소**를 쓴다 — 다른 프로세스의 방해는 시간을 늘리기만 하므로 최소값이 재현성이 높다. 편차는 `(중앙값 − 최소)/최소`로 재서 단일 이상치에 흔들리지 않게 했다(처음엔 `(최대 − 최소)`를 써서 재현성 양호한데도 58.8% 경고가 떴다).
- **종료 코드**: `0` 퇴행 없음 / `1` 퇴행 / `2` 기준선 없음 / `3` **판정 불가**(머신이 시끄러워 비교 무의미).
- **작성 중 고친 결함 6건** — 하네스 자체가 틀리면 이후 모든 주장이 무의미하므로 전부 기록한다:
  1. 중복률 역산을 닫힌 형태 근사식으로 하니 목표 0.68에 0.60이 나왔다(장비명이 명령 줄에 박혀 반복 블록도 완전히 동일하지 않다). 실측 기반 이분탐색으로 교체 → 오차 0.01 이내.
  2. 메모 웜 측정이 순수 dict 조회만 재서 511배라는 무의미한 값을 냈다. 실제 구현과 같은 래퍼(함수 호출 + dict 조회)로 교체.
  3. 퇴행 방향 판정이 `endswith("_speedup")`이라 `match_signature_memo_speedup_run` 같은 이름이 조용히 검사에서 빠졌다 — **메모 이득 퇴행이 감지되지 않는 버그**였다. 부분 문자열 매칭으로 교체.
  4. 중앙값과 최소값을 둘 다 비교해서, 코드 변경이 전혀 없는데 중앙값만 +12.6%로 튀어 퇴행이 보고됐다. 대표값은 최소값 하나로 하고 중앙값은 정보용으로 내렸다.
  5. 상대 변화만 봐서 `counter_row_ms`(0.3 ms)가 0.26 ms 흔들린 것이 +83.9% 퇴행으로 보고됐다. **절대 잡음 하한**(시간 2 ms, payload 5 KB, 배수 0.1배)을 추가해 상대·절대 조건을 둘 다 넘겨야 퇴행으로 본다.
  6. 신뢰도 신호를 `analyze_text` 편차만으로 잡으니 뒤쪽 측정 블록의 경합을 놓쳤다(편차 1.6%인데 `find_keyword_ms` +53%). 반대로 전체 블록의 `max`로 바꾸니 0.3 ms짜리 작은 블록 때문에 조용한 실행에서도 항상 판정 불가가 됐다. **전체 블록 편차의 p75**로 정착(조용한 실행 실측: median 1.2% / p75 2.9% / max 8.1%).
- **잡음 적응 임계값**: 유효 임계값 = `max(10%, 2.5 × 이번 실행의 편차 p75)`. 고정값 하나로는 두 실패를 동시에 피할 수 없다 — 10%로 두면 살짝 붐빈 실행(p75 6.2%)에서 +13.5%가 오탐이 되고, 20%로 올리면 진짜 15% 퇴행을 놓친다. "변화가 이 실행 자신의 잡음보다 도드라지는가"를 기준으로 삼는다.
- **검증**: 기준선을 인위적으로 조작해 3개 지표(시간 +98.5%, 메모 이득 −50.8%, payload +299.9%)가 모두 포착되고 exit 1이 되는지 확인. 조용한 실행 편차 p75 3.5%.
- **알려진 한계(정직하게 기록)**: 공유 컨테이너에서 8회 연속 `--check`를 돌린 실측에서 **7회 정상, 1회 오탐**(`find_keyword_memo_speedup_run` −34.9%). 이 환경의 CPU 경합이 17% 임계값도 넘긴 경우다. **퇴행이 보고되면 먼저 한 번 더 재서 재현되는지 확인할 것.** 개발 PC(조용한 Windows)에서는 더 안정적일 것으로 기대하지만 확인되지 않았다.

## 3단계 — 구조 개선

기능 동작에 영향이 있거나 범위가 넓다. 1·2단계로 이득을 확보한 뒤 착수한다.

### 3-1. 실시간 감시 폴링 payload 델타화 ✅ 완료

- **대상 파일**: `engine/realtime_monitor.py`(`state`), `api/log_analysis_run_api.py`(`get_realtime_monitor_state`), `web_ui/js/realtime-monitor-panel.js`
- **지금 동작이었던 것**: `state(tail=160)`은 계산이 1.5 ms(장비 30대)로 싸다. **문제는 전송량**이었다 — 폴링 1회당 701.7 KB, 0.8초 주기로 **877 KB/s**가 pywebview 브릿지를 통과했다(12대 364.6, 4대 138.4 KB/s). 프론트엔드는 받은 뒤 9개 render 함수를 전부 돌리고 `innerHTML`을 20곳에서 교체했다 — 그래서 클릭으로 고정한 교차 강조를 매 렌더마다 복원해야 했다.
- **payload 구성 실측**(장비 30대): `devices.lines` 617.7 KB(88.0%) · `devices.checklist` 43.8 KB(6.2%) · `analysis` 18.1 KB(2.6%) · `alerts` 15.6 KB(2.2%). 줄 델타가 주효하고, 나머지 섹션 생략이 남은 몫을 줄인다.
- **실측 이득**(장비 30대, tail=160, 장비마다 새 줄 1개가 들어온 회차):
  - payload **701.7 KB → 9.74 KB** = 0.8초 폴링 기준 **877.1 → 12.2 KB/s (72배)**
  - 새 줄이 없는 조용한 회차는 6.76 KB(대부분의 폴링이 여기다 — 사람이 명령을 치는 속도가 0.8초 주기보다 느리다)
  - 4대 138.4 → 2.0 KB/s, 12대 364.6 → 5.1 KB/s
  - 수용 기준(50 KB/s 이하)을 4배 여유로 충족. 하네스가 `state_dev*_delta_kb` / `_delta_shrink`로 계속 감시한다.
- **서버**(`realtime_monitor.py`): 줄마다 **전역 단조증가 `seq`**(장비별이 아니다 — 장비별로 매기면 커서 하나로 다른 장비 줄을 건너뛴다), 버퍼가 되감기는 사건(`reset`/`clear_alerts`)에는 `epoch`를 올린다. `state(tail, since=None)`이 `since={epoch, versions, devices:{장비:seq}}`를 받으면 그 이후 줄만 담고, 지문이 같은 섹션은 `None`으로 비운다. 장비별로 `line_seq`(서버 버퍼의 최신 seq)와 `resync`를 함께 돌려준다. **`since`를 생략하면 예전과 바이트 단위로 같은 전체 스냅샷** — 강제 재동기화가 그 경로를 쓴다.
- **원자성**(이 항목의 HIGH 리스크가 여기다): 델타 절단선 · 체크리스트 · 분석 · 고정 · 섹션 지문을 **같은 락 블록 안에서** 계산한다. 이 모듈이 존재하는 이유가 "세 패널이 같은 이벤트에서 파생되므로 갱신 시점이 어긋나면 '왼쪽 로그에는 보이는데 체크리스트는 정상'인 화면이 나온다"는 것이므로, 델타화가 그것을 깨서는 안 된다.
- **클라이언트**(`realtime-monitor-panel.js`): 렌더 함수들은 **여전히 완전한 상태만** 본다 — `rtmMergeState()`가 델타를 직전 사본에 합쳐 다시 완전한 상태로 만든 뒤 넘긴다. 그래서 렌더 쪽 분기가 늘지 않고 원자성도 유지된다. 그 위에 두 가지를 얹었다:
  - 안 바뀐 패널은 다시 그리지 않는다. DOM이 살아남으므로 **고정 강조를 매 폴링마다 복원할 필요가 없어졌다**(스크롤 위치·텍스트 선택도 유지된다).
  - 로그 박스는 교체가 아니라 **append**(`rtmAppendRtmLogLines`). 배치를 바꾸는 요인(장비 목록·심각도 버킷·보기 모드·`resync`)이 하나라도 걸리면 예전처럼 전부 다시 그린다.
  - 합친 결과가 불완전하면(서버가 생략했는데 되살릴 직전 값이 없다) 화면을 건드리지 않고 커서를 버려 다음 폴링에서 전체를 받는다. 빈 값으로 그리면 '오류가 사라졌다'는 잘못된 화면이 된다.
- **부수 수정**: 섹션 지문 중 `alerts`를 `alert_id` 목록으로만 냈던 것을 고쳤다. `resolve_alerts()`/`ignore_alerts()`는 경고를 지우지 않고 **제자리에서** `resolved`/`ignored` 표시만 남기므로(이력 자체가 점검 자료다) id 목록이 그대로다 — 지금은 이 패널이 `state["alerts"]`를 읽지 않아 증상이 없지만, 읽는 쪽이 생기는 순간 '해결됨'이 영원히 전달되지 않는 조용한 버그가 된다.
- **리스크**: HIGH(실현) / **공수**: L
- **검증**: `tests/test_realtime_delta.py`(18, 서버) — 하위 호환(`since` 없이 예전과 동일), 30회 누적 재구성, 버퍼 초과 강제 유발 후 `resync`, `epoch` 증가 2종, 미지 장비, 섹션 생략/재전송, **델타와 섹션이 한 스냅샷에서 나오는지**, seq 전역 유일성. `tests/test_realtime_delta_client.py`(21, 클라이언트, node) — 핵심은 **실제 서버로 24회차를 진행시키며 델타만 합친 결과가 같은 시점의 전체 스냅샷과 글자 하나까지 같은지** 보는 왕복 테스트다(조용한 회차 · 줄 추가 · 경고 발생 · 필터 변경 · 초기화 · 장비 목록 증감을 모두 지난다). 그 시나리오들이 실제로 발생하는지도 따로 확인한다 — 처음에 `adopt_devices()`로 '목록 축소'를 시도했다가 그 함수가 추가만 해서 해당 회차가 아무것도 검증하지 않는 상태를 만들었다.
- **하네스 보강**: `_noise_floor()`가 델타 지표에만 더 작은 바닥값(0.5 KB / 1 KB/s)을 쓴다. 전체 payload 기준(5 KB / 10 KB/s)을 그대로 적용하면 6.8 KB → 20 KB 같은 **3배 퇴행이 절대 조건에서 걸러져 조용히 통과**한다 — 이 항목의 이득이 전부 그 숫자에 있으므로 그러면 게이트가 없는 것과 같다. 크기 지표는 애초에 측정 잡음이 없다(같은 입력이면 JSON이 바이트 단위로 같다).
- **남은 확인**: 실제 SecureCRT 세션으로 경고 발생 → 복구 → 숨김 → 고정 시나리오를 돌려 세 패널이 어긋나지 않는지 육안 확인 — 이 컨테이너에는 pywebview/실장비가 없다.

### 3-6. 로그 파일명 규칙 통합 + run_id 정렬 불변식 ✅ 완료 (계획 수정됨)

**계획의 전제가 틀렸다.** 3-6 은 "run_id 포맷이 섞여 '최신 run' 판정이 조용히 틀린다"를 근거로 삼았는데, 확인해 보니 재현되지 않았다:

- run_id 생성은 `core/storage_service.create_run()` **한 곳**이고 `core.utils.format_run_id()`(`%Y-%m-%d_%H%M%S`)를 쓴다. 충돌 시 `_%f`를 덧붙이는데 접두부가 같아 정렬이 유지된다.
- **V0.5.0~V0.5.8 전부 같은 포맷**이었다(git 이력 확인). 섞인 적이 없다.
- 그 포맷들에 대해 **문자열 정렬 == 시각 정렬**이다(실측).

또 `strftime` 33곳(13개 포맷) 중 **되파싱되는 것은 1곳뿐**(`engine/inspection_report_builder.py`)이다. 나머지는 표시 전용이라 포맷이 달라도 정확성 문제가 없다 — 33곳을 일괄 수정하는 것은 근거 없는 변경이므로 하지 않았다.

**대신 실제로 남아 있던 위험을 처리했다**: 같은 **파일명 규칙을 파싱하는 코드가 네 곳에 복제**돼 있었다(`engine/log_analysis.py` 인라인, `api/log_analysis_run_api.py` 인라인, `api/log_file_browser_api.py` ×2). 네 곳이 지금은 같은 답을 낸다(실측). 문제는 규칙이 바뀔 때 한 곳만 고쳐지고, 그러면 장비명이 화면마다 달라진다는 것이다.

- **적용**: `core/log_naming.py` 신규 — 만드는 쪽(`api/terminal_inspection_api`)과 읽는 쪽이 같은 출처를 쓴다. 폴백 문자열(`unknown_time`)도 한 곳으로 모았다.
- **합치지 않은 것**: `engine/baseline_store.device_from_filename()`은 **다른 파일 집단**을 다룬다 — SecureCRT가 임의로 붙인 CRTlog 이름에서 장비를 추정하는 휴리스틱이라 첫 두 토큰이 숫자인지 보고 실패하면 첫 토큰을 쓴다. 실측 차이: `Core1_backup_config_v2.txt` → 점검로그 파서 `"v2"` / CRTlog 파서 `"Core1"`. 합치면 둘 중 하나가 반드시 깨진다. 그 차이를 테스트로 고정해, 나중에 "중복이네" 하며 합치려 할 때 이유를 알 수 있게 했다.
- **이 항목의 핵심 가치**: `run_id` **문자열 정렬 == 시각 정렬** 불변식을 테스트로 못박았다. 포맷을 바꾸면 실패한다. 이 실패 모드는 조용하고 파급이 크다 — '최신 run'을 잘못 고르면 보고서·대시보드·분석이 전부 다른 회차를 읽는다.
- **리스크**: LOW / **공수**: M
- **검증**: `tests/test_log_naming.py`(22)

## 하지 않을 것 (Non-goals)

- **정규식 통합 (31개 signature → 단일 alternation)** — 실측 결과 **2.6배 느리다**(264 ms → 705 ms). 키워드 17개 통합도 **2.7배 느리다**(109 ms → 292 ms). 원인: Python `re`는 패턴별 리터럴 접두사 최적화를 하는데 alternation으로 묶으면 그 최적화를 잃고, 문자열의 모든 위치에서 31개 대안을 백트래킹한다. **이 계획에서 가장 중요한 발견이다** — 직관적으로 가장 그럴듯한 최적화가 실제로는 퇴행이다.
- **리터럴 프리필터 게이트** — 순수 Python 루프 게이트는 0.96배(무효), C 레벨 126-토큰 단일 정규식 게이트는 0.39배(퇴행). 코퍼스의 71%가 게이트를 통과해 필터 효과가 없다.
- **`web_ui/index.html`의 script 태그 31개 번들링** — pywebview는 `file://`로 로드하므로 HTTP 왕복이 없다. 번들링 이득의 근거가 없다. **개선 불필요.**
- **`engine/collector.py` 수집 경로** — 이미 최적이다. 장비 단위 `WorkerPool` 병렬화(최대 50), 장비 내 명령은 SSH 세션이 stateful하므로 의도적 순차, 그리고 명령들을 하나의 bulk 텍스트로 묶어 왕복을 1회로 줄였다. 손대지 않는다.
- **`api/log_analysis_run_api.py`(910줄) 파일 분리** — 성능 이득이 없고, 믹스인 조합 순서 의존성(`LogFileBrowserApiMixin`, `SettingsApiMixin`과의 상호 참조)을 깰 위험만 있다. 성능 계획의 범위 밖이다.
- **`ARCHITECTURE.md` Known follow-ups #1/#3 (run 생성 경로 통합, 미연결 매니저 메서드 13개)** — 구조 부채지만 성능과 무관하다. 이 계획에서 다루지 않는다.
- **`core/storage_service.py` ⇄ `engine/run_manager.py` 순환 import 해소** — 지연 import로 이미 동작하고, 시작 비용에 기여하지 않는다(1-1의 무거운 의존성과 무관). 성능 사유로는 착수하지 않는다.
- **전면 리팩터링** — 동작 중인 실무 도구다. 각 항목은 독립 커밋으로 되돌릴 수 있어야 한다.

## 수용 기준

숫자로 판정한다. 모두 0-2 벤치마크 하네스의 고정 시드 코퍼스로 측정한다.

1. **0단계** ✅ — 테스트가 현재 코드에서 전부 통과한다(작성 시 69개 → 현재 272개)(`python -m pytest tests/ -q`). 하네스 측정 편차 p75 3.5%(≤5%). 기준선 조작 시 퇴행 3건을 모두 포착하고 exit 1을 낸다. 8회 연속 `--check`에서 7회 정상(1회는 컨테이너 경합에 의한 오탐 — 위 한계 참고).
2. **1-1** ✅(부분) — 16개 믹스인이 세 패키지 **미설치 상태에서 전부 import** 됨을 확인했다. 남은 확인: Windows 에서 `python -X importtime main.py` 로 창이 뜨기까지의 시간이 **1.0초 이상** 단축되는지.
3. **1-2** ✅ — `AppPaths.crt_log_root()` 반복 호출 **0.22 us/call**(기준 1 us 이하, 변경 전 9.8 us). 남은 확인: 앱 실행 중 `CRTlog` 를 지운 뒤에도 실시간 감시가 동작하는지(수동 확인 필요 — 쓰기 경로가 각자 `makedirs` 하는 것은 코드로 확인했다).
4. **2-1/2-2** ✅ — `match_signature_memo_speedup_run` **3.11배**(기준 3.0), `find_keyword_memo_speedup_run` **3.47배**(기준 3.3). `analyze_text` 누적 **2.72배**(70.2 → 25.8 ms). 장비 20대 회차에서 메모 on/off findings **완전 일치**. 메모 상한 준수 확인. 남은 확인: **실제 수집 로그**로 on/off 일치를 한 번 더 대조(합성 코퍼스로만 확인했다).
5. **2-3** — 하지 않기로 결정(실측 기여도 0.91% 줄, 약 0.1 ms). 별도 수용 기준 없음.
6. **3-1** ✅ 장비 30대에서 폴링 payload **12.2 KB/s**(기준 50 KB/s 이하, 이전 877.1 KB/s). `seq` 재동기화를 버퍼 초과로 강제 유발해 확인했고, 델타만 합친 상태가 24회차 내내 전체 스냅샷과 일치한다. 실장비 세션 육안 확인은 남아 있다(이 환경에 pywebview/장비가 없다).
7. **3-2** ✅ — 점검 직후 두 번째 패스의 추가 파싱 **0회**(12회 → 0). 흐름 전체 약 2배. 파일을 덮어쓰면 다음 조회에서 새 판정이 나오는 것을 크기가 같은 경우까지 테스트로 확인. 남은 확인: **실제 수집 로그**로 점검 → 대시보드 → 보고서 → AI 네 화면의 수치가 일치하는지 육안 대조.
8. **3-3** ✅ — `get_workspace_overview()`가 run당 `session.json`/`metadata.json`/`health_score.json`을 각각 **1회만** 읽는다(파일 읽기 횟수로 검증). run 20개에서 27.4 → 13.7 ms. 활성 run 우선순위(진행 중 > 최신) 유지.
9. **3-4 / 3-5** — 하지 않기로 결정(실측 0.16~1.24 ms / 0.65 ms). 3-5는 기능 후퇴(점검 직후 30초 낡은 수치)까지 따라오므로 순수 손실이다. 별도 수용 기준 없음.
10. **3-6** ✅ — `run_id` **문자열 정렬 == 시각 정렬** 불변식이 테스트로 고정됐다(포맷을 바꾸면 실패). 파일명 파서 4중 복제가 하나로 통합되고, CRTlog 파서와의 의도적 차이가 테스트로 문서화됐다.
11. **전 단계 공통** ✅ — 골든 테스트가 모든 커밋에서 통과했고, 각 항목이 독립 커밋이라 어디서 멈춰도 그 시점까지의 이득이 남는다.
